# T09-001 · Shared DTOs for ops, costs and attention resolutions

Status: APPLIED
Requested by: T09 · Wave: W3
Target: `packages/contracts/src/dto/ops.ts` (new), `packages/contracts/src/dto/costs.ts` (new), `packages/contracts/src/dto/index.ts` (owner: T01)
Kind: contract

## Problem
ARCHITECTURE §8 lists `GET /ops/live`, `/ops/kpis`, `/ops/activity`, `/ops/alerts`, `/ops/operators/:userId/trail`, `GET /costs/rollup`, `GET /attention` and `POST /attention/:kind/:id/resolve`, but `packages/contracts` has no zod schemas for their responses. The web app and the T10 integration tests therefore cannot validate these payloads against a shared contract. Contracts are frozen after T01 (R4), so T09 cannot add them.

Attention resolutions also need a home. Rejected mutations, pending media, stale devices and diagnostics have no `resolvedAt`, `resolvedById` or `resolutionNote` fields in the db schemas, so T09 records a resolution as an `ActivityEvent` (`entityType` `DEVICE` or `USER`, `action` `attention.resolved`, `meta: { kind, itemId, note }`) with a deterministic id `attention:<kind>:<id>`.

## Proposed change
1. Add `packages/contracts/src/dto/ops.ts` with zod schemas mirroring the TypeScript interfaces in `packages/core/src/modules/ops/dto.ts`:
   - `OpsKpisDTOSchema`;
   - `LiveOperatorDTOSchema`, `LiveWorkOrderDTOSchema`, `LiveReportDTOSchema`, `LiveRentalDTOSchema`, `LiveAssetDTOSchema` and `OpsLiveDTOSchema`;
   - `OpsAlertDTOSchema` and `OpsAlertsDTOSchema`;
   - `OpsActivityItemDTOSchema` and `OpsActivityDTOSchema`;
   - `TrailPointDTOSchema` and `OperatorTrailDTOSchema`;
   - `AttentionKindEnum` (`REJECTED_MUTATION | MEDIA_PENDING | STALE_DEVICE | DIAGNOSTIC`), `AttentionItemDTOSchema`, `AttentionListDTOSchema`, `AttentionResolveInputSchema` (`{ note: string 1..1000 }`) and `AttentionResolutionDTOSchema`;
   - `KpiKeyEnum`, `KpiRangeEnum` and `AlertTypeEnum`.
2. Add `packages/contracts/src/dto/costs.ts` with `CostGroupByEnum` (`asset | site | plot | season | category | crop`), `CostRollupRowSchema`, `CostRollupFiltersSchema` and `CostRollupDTOSchema`, mirroring `packages/core/src/modules/costs/dto.ts`.
3. Optional, in `packages/db`: add `resolvedAt`, `resolvedById` and `resolutionNote` to `rejected_mutations` so that resolution no longer relies on activity events.

## Workaround in place
The DTOs are defined as TypeScript interfaces in `packages/core/src/modules/{ops,costs}/dto.ts`. Route inputs are validated with local zod schemas inside the core services. The web imports these types only (`import type`), so no core runtime code reaches the client bundle. Resolutions are stored as idempotent `ActivityEvent` rows. A second resolver gets `ALREADY_RESOLVED` with `details: { resolverName, resolvedAt, note }`.

## Impact if rejected
The payloads stay typed only through the core interfaces, with no runtime validation on the client. Attention resolutions keep living in `activity_events`.

## Resolution

The orchestrator applied items 1 and 2 at the W3 gate. `packages/contracts/src/dto/ops.ts` defines `SlaStateEnum`, `KpiKeyEnum`, `KpiRangeEnum`, `AlertTypeEnum`, `AttentionKindEnum`, the live-frame schemas (`LiveOperatorDTOSchema` through `OpsLiveDTOSchema`), `OpsKpisDTOSchema`, the alert, activity and trail schemas, and `AttentionItemDTOSchema`, `AttentionListDTOSchema`, `AttentionResolveInputSchema` and `AttentionResolutionDTOSchema`. `packages/contracts/src/dto/costs.ts` defines `CostGroupByEnum`, `CostRollupRowSchema`, `CostRollupFiltersSchema` and `CostRollupDTOSchema`. Both are exported from `@agrorende/contracts/dto` and covered by `dto/ops.test.ts`. The core `modules/ops/dto.ts` and `modules/costs/dto.ts` now take their enum lists and union types from these contracts enums, and keep their readonly interfaces as mirrors of the schemas for the services. Item 3, adding resolution fields to `rejected_mutations` in `packages/db`, is DEFERRED-T10: the activity-event workaround is idempotent and tested, and a schema change to the database package is better made together with the T10 integration tests.
