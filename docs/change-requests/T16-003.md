# T16-003 · Align the api-client search and analytics response types with the server

Status: OPEN
Requested by: T16 · Wave: W6
Target: `packages/api-client/src/types.ts` (owner: T02)
Kind: contract

## Problem
The server responses that T16 implemented differ from the placeholder types in the api-client:

- `GET /search` returns light hits rather than full DTOs. A full `WorkOrderDTO` or `RentalDTO` per hit is heavy, and the palette needs only a title, a subtitle and a link. The real shape (`packages/core/src/modules/ops/search.ts`) is:

  ```ts
  interface SearchHit { id: string; type: SearchType; title: string; subtitle: string | null; href: string }
  type SearchResponse = { q: string; tookMs: number } & { [K in "assets" | "workOrders" | "fieldReports" | "rentals" | "customers" | "sites"]: SearchHit[] };
  ```

- `GET /ops/analytics` returns more fields than `AnalyticsResponse` declares: `from`, `to`, `seasonId`, `summary: number | null`, an optional `cost: CostRollupDTO` for the `cost` metric, and points shaped `{ key, label, value, secondary?: number | null }` (`packages/core/src/modules/ops/analytics.ts`).

The web app uses the core types through its own typed fetch helpers, so nothing is blocked today. The mobile app and any other api-client consumer would read the wrong shape.

## Proposed change
Update `SearchResponse` and `AnalyticsResponse` (and `AnalyticsSeriesPoint`) in `packages/api-client/src/types.ts` to the shapes above.

## Impact if not applied
api-client consumers get wrong types for two endpoints. There is no runtime impact on the web app.
