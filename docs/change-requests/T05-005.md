# T05-005 · Apple refresh-token revoke seam for `auth.appleRevoke`

Status: APPLIED
Requested by: T05 · Wave: W2
Target: `packages/core/src/auth/apple.ts` (owner: T02)
Kind: seam signature

## Problem
The worker runs `auth.appleRevoke` with retries, but no core function revokes the stored Apple refresh token yet.

## Proposed change
Export `revokeAppleRefreshToken({ orgId, identityId }: { orgId: string; identityId: string }): Promise<void>` from `packages/core/src/auth/apple.ts`. It should load and decrypt the identity's refresh token, call `https://appleid.apple.com/auth/revoke` with the client secret built from `APPLE_TEAM_ID`, `APPLE_CLIENT_ID`, `APPLE_KEY_ID` and `APPLE_PRIVATE_KEY`, and delete the identity once Apple confirms. The job payload carries only ids, never the token.

## Workaround in place
`apps/worker/src/jobs/index.ts` loads that file when it exists. Otherwise the job throws, so BullMQ retries it 5 times with exponential backoff. Failures are logged by id, attempt and error name only, and the error the job rethrows is a fixed `APPLE_REVOKE_FAILED`, so a token can never reach the logs or Redis. At startup the worker warns when the `APPLE_*` secrets are absent and fails when they are only partly set.

## Impact if rejected
Apple identities are not revoked when an account is deleted.

## Resolution
Deferred to T10. Revoking the Apple refresh token needs the Sign in with Apple provider wiring: the client secret built from the `APPLE_*` secrets, decryption of the stored refresh token and the identity lifecycle in `packages/core/src/auth/apple.ts`. T10 wires the OAuth providers, and `arctic` was added to `packages/core` at this gate for that purpose. Until then the worker's `auth.appleRevoke` job keeps its safe workaround: it retries with backoff and never logs or stores the token.

## T10 resolution
T10 added `packages/core/src/auth/apple.ts`, which exports `revokeAppleRefreshToken({ orgId, identityId })` with the requested signature. The function loads the identity scoped to the organisation and returns quietly when it no longer exists, so a retried job is idempotent. It refuses identities whose provider is not Apple. When the identity holds a refresh token, the function decrypts it with AES-256-GCM using `AUTH_ENCRYPTION_KEY`. The encrypted payload also records the client id that received the token (the web Services ID or the iOS bundle id), and that client id is used for the revocation. In production, the function posts to `https://appleid.apple.com/auth/revoke` with an ES256 client secret signed with `APPLE_TEAM_ID`, `APPLE_KEY_ID` and `APPLE_PRIVATE_KEY`. Locally, it posts to the `revocation_endpoint` that the mock issuer advertises in its discovery document, and it sends no secret. The identity is deleted only after Apple answers with success, and a failure throws so that the worker's retry policy applies. The token is never logged. The worker already loads this file in `apps/worker/src/jobs/index.ts`, so no worker change was needed. The OAuth callback and the native `POST /auth/apple` route now store the encrypted refresh token on the identity whenever Apple returns one. The behaviour is covered by `packages/core/src/auth/oauth.test.ts`, which runs against the local mock.
