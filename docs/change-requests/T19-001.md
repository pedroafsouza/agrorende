# T19-001 · Describe the site build and artifact in the releasing guide

Status: APPLIED
Requested by: T19 · Wave: W7
Target: `docs/RELEASING.md` (owner: T18)
Kind: documentation

## Problem
`docs/RELEASING.md` still says that the deploy copies the static site "when `apps/site` exists". Since T19, `apps/site` always exists, and the workflows changed accordingly:

- `deploy.yml` always builds the site with the target environment's `SITE_URL` (`https://${{ vars.SITE_HOST }}`) and `APP_URL`, plus the optional `SITE_*` variables, and always copies `apps/site/out/` to `/srv/agrorende/site` with `rsync --delete`.
- `release.yml` publishes the `site` artifact as a single `site.tar.gz` archive of `apps/site/out` instead of the loose directory.
- `ci.yml` builds the site with `SITE_URL=http://localhost:3191` and runs the site's Playwright checks and Lighthouse budgets in the `build` job.

## Proposed change
In step 4 of the deploy section, drop "(when `apps/site` exists)" and add one sentence: the site is built on the runner for the target environment, so canonical, hreflang and sitemap URLs use that environment's `SITE_HOST`. In the release section, name the `site` artifact as `site.tar.gz`. List the optional repository or environment variables `SITE_SHOW_PRICES`, `SITE_WHATSAPP`, `SITE_CONTACT_EMAIL`, `SITE_PRIVACY_EMAIL`, `SITE_APP_STORE_URL` and `SITE_PLAY_STORE_URL`, and link `docs/SITE.md`.

## Workaround in place
`docs/SITE.md` describes the build, the variables and the deploy path in full.

## Impact if rejected
The releasing guide slightly understates what the deploy does; nothing breaks.

## Resolution
Applied by the orchestrator at the W7 gate: `docs/RELEASING.md` §4.1 names the `site.tar.gz` artifact and the CI site checks, and §5 step 4 describes the per-environment site build, the optional `SITE_*` variables and links `docs/SITE.md`.
