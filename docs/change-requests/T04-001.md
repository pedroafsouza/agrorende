# T04-001 · Export the core master-data modules by package name

Status: APPLIED
Requested by: T04 · Wave: W2
Target: `packages/core/package.json`, `packages/core/src/index.ts` (owner: T01)
Kind: dependency

## Problem
`@agrorende/core` exports only its root entry. The web API routes need the services and queries of `modules/assets`, `modules/sites`, `modules/seasons`, `modules/customers` and `modules/checklists`, and ESLint bans `@agrorende/*/src/*` imports.

## Proposed change
Add a subpath export for each module to `packages/core/package.json`, for example `"./modules/assets": "./src/modules/assets/index.ts"`, and likewise for sites, seasons, customers and checklists. T05-001 asks for the same pattern for locations and exports, so a single `"./modules/*": "./src/modules/*/index.ts"` export would cover both requests.

## Workaround in place
`apps/web/src/lib/core.server.ts` is the only web file that reaches the module sources, through a relative path. Every route imports from that adapter, so only that file changes when the export lands.

## Impact if rejected
The relative imports keep working, but they depend on the repository layout and bypass the package boundary that ESLint is meant to enforce.

## Resolution
Applied at the W2 gate. `packages/core/package.json` exports `./modules/*` (mapped to `./src/modules/*.ts`), so `@agrorende/core/modules/assets/service` and its siblings resolve by package name. `apps/web/src/lib/core.server.ts` now imports every master-data module that way instead of through relative paths. `@agrorende/db` was added to `transpilePackages` in `apps/web/next.config.ts`.
