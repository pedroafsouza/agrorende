# T04-004 · Have `withApi` build the core ctx from the access token

Status: APPLIED
Requested by: T04 · Wave: W2
Target: `apps/web/src/server/withApi.ts` (owner: T01)
Kind: other

## Problem
`ApiContext.core` is optional and is never filled, and `readSession` only checks that the cookies are present. A route cannot rely on a verified `orgId`, `userId` or role.

## Proposed change
In `withApi`, verify the `ar_access` cookie or the bearer token with `verifyAccessToken(token, JWT_SECRET)`. Then build `core: Ctx` from the claims, enforce `options.roles` (`FORBIDDEN`), and return `UNAUTHENTICATED` when the token is missing or invalid.

## Workaround in place
`authenticate()` in `apps/web/src/lib/core.server.ts` performs these steps inside the T04 routes, and its route wrapper uses it.

## Impact if rejected
Each owner of web routes has to repeat the token check.

## Resolution
Applied at the W2 gate. `apps/web/src/server/withApi.ts` reads the `ar_access` cookie or the `Authorization: Bearer` header and verifies the token with `verifyAccessToken` and `JWT_SECRET`. It then builds the core `Ctx` and exposes it as `api.core`, and checks the route's allowed roles. A missing token yields `UNAUTHENTICATED` and an invalid or expired one yields `TOKEN_EXPIRED`. A role mismatch yields `OFFICE_ROLE_REQUIRED` when a FIELD user calls an office-only route, and `FORBIDDEN` otherwise. The `ar_platform` cookie path still works. `route()` in `apps/web/src/lib/core.server.ts` passes its roles to `withApi` and uses `api.core`, with the old `authenticate` adapter kept as a fallback. A new `routeContextOf` helper reads the Next.js route context, which handlers receive as `unknown`.
