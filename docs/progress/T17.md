## Done

### Comments (FR, WO and RN threads)
- **Core comments module.** `packages/core/src/modules/comments/{service,mutations,dto}.ts` now hold the real `comment.create` handler, replacing the P1 stub, plus `listComments` and `createCommentFromInput`.
  - Comments are allowed on field reports, work orders and rentals. Any other parent type is refused.
  - A user who cannot see the parent record gets `NOT_FOUND`, and so does a request from another organisation.
  - Replaying a mutation id is idempotent: the stored row is returned and nobody is notified again. A replay from a different author is `VALIDATION_FAILED` (`commentIdReuse`).
- **REST routes.** `apps/web/src/app/api/v1/comments/route.ts` serves `GET` and `POST /comments`.
- **Web thread.** `apps/web/src/features/comments/**` contains the thread component (empty state, list with author names, trimmed post, inline error for an empty comment) and its server helpers.
- **Mobile thread.**
  - `apps/mobile/src/features/comments/**` and `apps/mobile/src/sync/mutators/comments.ts` provide the thread on the work-order, report and rental detail screens.
  - A comment is inserted locally at once and goes through the outbox, so it works offline.
  - Rows that have not been sent yet show a pending marker (`comment-pending-<id>`). The thread shows an offline hint and read-only states.
  - Copy lives in `src/i18n/*/comments.json`.
- **Comment notification behaviour.** When a comment is created, the server sends a `COMMENT_ADDED` notification to the record's creator, its current assignee and every earlier commenter, and never to the author. It also sends a `syncPoke` to each recipient's room, so an open phone pulls the new comment straight away. A replayed offline comment syncs exactly once and does not notify twice.

### FR-04 photo annotation
- `src/components/MediaCapture/{annotation.ts,AnnotateSheet.tsx,Thumbnails.tsx,index.tsx}`.
- Photo drafts get a pen button. The sheet lets the user draw arrows and circles over the photo with Skia, with undo, cancel and save.
- The sheet is lazy-loaded so screens that only show thumbnails never load Skia.
- **Annotation storage.**
  - The flattened JPEG is written as `media/<id>_annotated.jpg` with the same media id. The `media_files` row's `localUri`, `thumbUri` and `sizeBytes` are updated to point at it, so the upload sends the annotated photo.
  - A photo can only be annotated while its row is still `WAITING_PARENT`. Once upload has started, the button is not offered.
  - The original `media/<id>.<ext>` is kept until the row is `DONE`, so an interrupted annotation never loses the photo. `pruneAnnotationOriginals` then removes it; wiring that call into the sync loop is T17-004.
  - Annotating again replaces the previous flattened copy.
  - When the file store cannot write temporary files, the button is hidden.

### Jobs P1 (WO arrival prompt, While I'm here, jobs map)
- **Arrival prompt.** `src/features/jobs/{arrivalPrompt.ts,useArrivalPrompt.ts}` and `src/location/watch.ts`.
  - **Arrival timing.**
    - Foreground location is watched only while the job is `EN_ROUTE` and only if permission was already granted. The app never asks for permission for this helper.
    - Updates use balanced accuracy, every 25 m or 15 s.
    - The target is the job's destination pin, otherwise the site pin. The radius is the site's `radiusM`, or 200 m by default.
    - Fixes with an accuracy worse than 150 m are ignored.
  - **Showing and answering the prompt.**
    - The prompt appears at most once per work order per app session.
    - After *Not yet* it stays quiet for 10 minutes.
    - It never arrives automatically: only *I'm here* sends the `arrive` transition.
    - *Wrong place* (EC-WO-21) closes the prompt and posts the measured point to the office as a comment on the work order.
- **While I'm here.** `src/features/jobs/JobDetailScreen.tsx` adds a "While I'm here" entry for a job in the field. It opens a new report prefilled with the job's machine and site.
- **Jobs map.** `src/features/jobs/{JobsMap.tsx,loadJobsMap.ts,JobsScreen.tsx,logic.ts}`.
  - The Jobs tab has a List/Map switch.
  - The map shows one pin per job, coloured by priority, with a legend. Tapping a pin opens the job.
  - The map module loads only when the user switches to it.

## Assumptions
- The arrival prompt's memory (shown and declined jobs) lives in memory for the app session only. Restarting the app may ask once more for the same job, which is harmless because the prompt never changes anything by itself.
- There is no mutation for "update the site point", so *Wrong place* sends the measured coordinates and accuracy to the office as a comment on the work order. The office can then fix the site pin.
- The FR-12 duplicate hint reuses the existing "open the existing case" action. Adding information to an existing case is done through its comment thread instead of a new merge flow.
- Push registration runs when the tabs mount, so it happens after sign-in and after every cold start, and the server sees token changes.
- `deviceUsersNative.ts` repeats the per-user profile and database paths instead of importing them from the session bootstrap, which T17 does not own.
- The web mount-point test in `apps/web/src/features/comments/mountPoints.test.tsx` (a T17 path) asserted that the T14, T15 and T16 mount points render nothing. Those components are now real, so the rows were reduced to "the mount point is still exported"; their owners test the behaviour.
- The Maestro flows target the development build (`app.agrorende.field.dev`) and the demo seed. They use `APP_ID`, `SITE_LAT` and `SITE_LNG` environment overrides. The storage-low and clock-skew flows need the emulator to be prepared by hand (fill the disk, move the clock), as their headers say.
