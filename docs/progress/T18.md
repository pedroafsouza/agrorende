- **T18.8 (`.github/workflows/release.yml`).**

  - A `vX.Y.Z` tag promotes without rebuilding. It verifies that the tag points at a commit on `main` and that staging deployed that exact commit successfully, re-tags each image digest with `docker buildx imagetools create`, checks that the digests match, and creates the GitHub release.

  - The deploy job runs these steps in order:
    1. Renders `.env` from the GitHub Environment secrets and variables (`infra/scripts/render-env.py`) and validates it (`infra/scripts/validate-env.sh`).

    3. Logs in to GHCR with a read-only token, pulls `IMAGE_TAG` and runs the `migrate` one-off.
    4. Rolls worker and realtime, then web, then Caddy and backup, waiting for health at each step.
    5. Checks health and runs the smoke test from the runner.
  - The job sets `environment: <name>`, so production goes through the GitHub Environment's required reviewers. SSH uses `StrictHostKeyChecking yes` with a pinned known-hosts entry.

## Assumptions

- **Image size.** The `node:24-bookworm-slim` base alone is about 268 MB unpacked, so I read the "<250 MB" image budget as compressed (registry) size. Realtime, worker and migrate are 82–87 MB compressed. Web is 102 MB compressed and 465 MB unpacked.
- **Bundling instead of `pnpm deploy` output.** The images ship esbuild bundles of each app, with only the externals that cannot be bundled installed through a production-only dependency tree. This is smaller than a full `pnpm deploy --prod` output and keeps the TypeScript sources out of the images. The `pnpm deploy` intent (production dependencies only, no dev files) is preserved.
- **Migrations.** The `migrate` target runs the bundled `packages/db` migration runner instead of `pnpm db:migrate`, because that script uses `tsx`, which is a dev dependency. The behaviour is the same: indexes, then data migrations.
- **Legacy builder.** The local Docker (colima, no buildx) uses the legacy builder, so the Dockerfiles avoid BuildKit-only syntax such as cache mounts and heredocs. They also build under BuildKit in CI.
- **Realtime URL in the web image.** The web client reads `NEXT_PUBLIC_REALTIME_URL` at build time. To keep one image across environments, the web build embeds a placeholder that `web-entrypoint.sh` replaces with the runtime value when the container starts. Change request T18-003 asks for a runtime setting.
- **"A15" in T18.8.** The reference is ambiguous. I read it as "the staged digest": promotion requires a successful staging deployment of the tagged commit and promotes exactly the digests that were deployed.
- **Public site.** `apps/site` does not exist yet, so the site build and upload steps in `release.yml` and `deploy.yml` run only when `apps/site/package.json` is present. T19 owns the site integration.
- **Local OIDC.** In the T18.7 run, `GOOGLE_OIDC_ISSUER` points at the mock on `localhost:4003`, which the containers cannot reach. The smoke uses password login, so this did not affect the result. Real deploys are protected by `validate-env.sh`.
- **bash 5.** `validate-env.sh` uses associative arrays and needs bash 4 or later. GitHub runners and the VM have bash 5. macOS `/bin/bash` 3.2 cannot run it, so I ran it locally inside a container.
